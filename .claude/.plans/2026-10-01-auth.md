# План: авторизация в API (пользователи + JWT)

## Context

Сейчас в `../../apps/api` есть только каркас: `PrismaModule`, `HealthModule`, проверка env через zod и глобальный `ZodValidationPipe`. Нужны пользователи и авторизация: регистрация, логин, логаут, смена пароля через JWT. Решения согласованы с пользователем:

- **токены:** короткоживущий access JWT плюс refresh JWT, сессии хранятся в БД;
- **передача:** httpOnly cookie;
- **хеш паролей:** argon2id;
- **данные:** проекты привязываются к владельцу (`Project.ownerId`).

## Зависимости (`../../apps/api/package.json`)

`@nestjs/cqrs`, `@nestjs/jwt`, `argon2`, `cookie-parser`; dev: `@types/cookie-parser`. Passport не используем: достаточно своего guard поверх `JwtService`, так получается проще.

## Схема БД (`../../apps/api/prisma/schema.prisma`) + миграция `auth`

```prisma
model User {
  id                String    @id @default(uuid()) @db.Uuid
  email             String    @unique            // хранится в lowercase
  firstName         String
  lastName          String
  passwordHash      String
  isActive          Boolean   @default(true)
  lastLoginAt       DateTime?
  passwordChangedAt DateTime?
  sessions          Session[]
  projects          Project[]
  createdAt / updatedAt
  @@map("users")
}

model Session {                                   // одна запись = одно устройство/логин
  id         String    @id @default(uuid()) @db.Uuid
  userId     String    @db.Uuid  (onDelete: Cascade)
  tokenHash  String                               // sha256 текущего refresh-токена
  userAgent  String?
  ip         String?
  expiresAt  DateTime
  revokedAt  DateTime?
  createdAt / updatedAt
  @@index([userId])
  @@map("sessions")
}
```

У `Project` появляется обязательное поле `ownerId` (связь с `User`, `onDelete: Cascade`) и `@@index([ownerId])`. Если в таблице `projects` уже есть строки, миграция упадёт. Для dev-базы тогда нужен `prisma migrate reset`.

## Общие контракты (`../../packages/shared/src/auth.ts`, экспорт из `index.ts`)

- `RegisterSchema`: firstName, lastName (1–100, trim); email (`z.email()`, trim + toLowerCase); password (8–128).
- `LoginSchema`: email, password.
- `ChangePasswordSchema`: currentPassword, newPassword (новый должен отличаться от текущего, проверка через `.refine`).
- `PublicUserSchema` / тип `PublicUser`: id, email, firstName, lastName, createdAt. Хеш пароля не отдаётся никогда.

## Взаимодействие модулей через CQRS (`@nestjs/cqrs`)

Правило: модули **не импортируют** провайдеры друг друга (repository и service не экспортируются). Межмодульные вызовы идут только через шины:

- `CommandBus` — изменить состояние;
- `QueryBus` — прочитать данные;
- `EventBus` — оповестить о случившемся.

Внутри модуля сервисы и репозитории вызываются напрямую.

- `CqrsModule.forRoot()` подключается в `AppModule`.
- Типизация результата: `class X extends Command<R>` / `Query<R>` из `@nestjs/cqrs` v11, тогда `commandBus.execute(new X())` возвращает `Promise<R>` без ручных кастов.
- Публичный API модуля — файл `src/<module>/contracts/index.ts`. В нём лежат классы команд, запросов, событий и read-модели. Импортировать из чужого модуля можно **только** из `contracts`.
- Раскладка внутри модуля: `commands/`, `queries/`, `events/` — по файлу на класс плюс handler рядом. Handlers регистрируются в `providers` модуля.

## Модули API

**`src/users/`** (`UsersModule`, ничего не экспортирует)

- `users.repository.ts`: единственное место, где идёт обращение к `prisma.user`. Методы: `findById`, `findByEmail`, `create`, `updatePassword(id, hash)` (заодно выставляет `passwordChangedAt`), `touchLastLogin`.
- `users.mapper.ts`: `toPublicUser(user)` → `PublicUser`.
- `contracts/`:
  - команды:
    - `CreateUserCommand({ firstName, lastName, email, passwordHash })` → `PublicUser`. Если email занят, бросает `ConflictException` (обрабатывается `P2002`). Публикует `UserRegisteredEvent`.
    - `ChangeUserPasswordCommand({ userId, passwordHash })` → `void`. Публикует `UserPasswordChangedEvent`.
    - `RecordUserLoginCommand({ userId })` → `void` (обновляет `lastLoginAt`).
  - запросы:
    - `GetUserByIdQuery(userId)` → `PublicUser | null`.
    - `GetUserCredentialsQuery({ email } | { userId })` → `UserCredentials | null`, где `UserCredentials = { id, passwordHash, isActive }`. Это внутренняя read-модель для auth, наружу через HTTP не уходит.
  - события: `UserRegisteredEvent(userId)` и `UserPasswordChangedEvent(userId)`. Сейчас это точки расширения, обработчиков пока нет. Например, позже на `UserRegisteredEvent` можно создавать проект по умолчанию.
- Хеширование пароля выполняет auth, а users получает уже готовый хеш. Так users ничего не знает об argon2.

**`src/auth/`** (`AuthModule`). С users общается только через `CommandBus`/`QueryBus` и `contracts` из users.

- `password.service.ts`: `hash` и `verify` на argon2id. Есть `verifyDummy()`: прогоняет проверку против фиктивного хеша, чтобы по времени ответа нельзя было узнать, существует ли email.
- `sessions.repository.ts`: `create`, `findActive(id)` (revokedAt = null и expiresAt > now), `rotate(id, tokenHash, expiresAt)`, `revoke(id)`, `revokeAllForUser(userId, exceptId?)`.
- `tokens.service.ts`: подписывает и проверяет JWT. Payload: `{ sub: userId, sid: sessionId }`. Секреты и TTL у access и refresh разные. Хеш refresh-токена считается через `sha256`: токен высокоэнтропийный, argon2 для него не нужен.
- `auth.service.ts` (оркестратор; к пользователям обращается через шины):
  - `register`: хеширует пароль и вызывает `CreateUserCommand` (на занятый email ответ 409), затем открывает сессию.
  - `login`: получает пользователя через `GetUserCredentialsQuery({ email })` и проверяет пароль. При неверном email или пароле, а также при `!isActive` отвечает одной и той же 401. При успехе вызывает `RecordUserLoginCommand` и открывает сессию.
  - `refresh`: проверяет JWT и находит активную сессию по `sid`. Если хеш не совпал, значит токен использован повторно: отзываются **все** сессии пользователя и возвращается 401. Иначе выполняется ротация.
  - `logout`: отзывает текущую сессию, повторный вызов безопасен.
  - `changePassword`: получает пользователя через `GetUserCredentialsQuery({ userId })` и проверяет текущий пароль. Затем вызывает `ChangeUserPasswordCommand` с новым хешем, отзывает все остальные сессии (это собственный репозиторий auth) и ротирует текущую.
  - `me`: вызывает `GetUserByIdQuery`.
  - Внутренний `issueSession(user, meta)`: создаёт `Session` и возвращает пару токенов.
- `auth.cookies.ts`: `setAuthCookies(res, tokens)` и `clearAuthCookies(res)`. Параметры cookie:
  - `access_token`: `path=/`, maxAge = access TTL;
  - `refresh_token`: `path=/auth`, maxAge = refresh TTL;
  - у обоих `httpOnly`, `sameSite=lax`, `secure` при `NODE_ENV=production`.
- `guards/jwt-auth.guard.ts`: регистрируется глобально через `APP_GUARD` в `AuthModule`.
  - Пропускает маршруты с `@Public()`.
  - Иначе читает cookie `access_token`, проверяет подпись и находит активную сессию по `sid`.
  - Благодаря проверке сессии логаут и смена пароля действуют сразу, а не после истечения access-токена.
  - В `req.user` кладёт `{ userId, sessionId }`.
- `decorators/public.decorator.ts`, `decorators/current-user.decorator.ts`.
- `auth.controller.ts`, DTO создаются через `createZodDto` из схем shared:

| Метод | Маршрут          | Доступ                                                   | Ответ                      |
| ----- | ---------------- | -------------------------------------------------------- | -------------------------- |
| POST  | `/auth/register` | public                                                   | 201 `PublicUser` + cookies |
| POST  | `/auth/login`    | public                                                   | 200 `PublicUser` + cookies |
| POST  | `/auth/refresh`  | public (refresh cookie)                                  | 204 + новые cookies        |
| POST  | `/auth/logout`   | public, отзывает сессию из refresh cookie, если она есть | 204, cookies очищены       |
| PATCH | `/auth/password` | auth                                                     | 204 + новые cookies        |
| GET   | `/auth/me`       | auth                                                     | `PublicUser`               |

`/health` помечается `@Public()`.

## Тесты

Handlers users (`create-user.handler.spec.ts`: на `P2002` бросается 409 и публикуется событие) — с замоканным репозиторием и `EventBus`.

`src/auth/auth.service.spec.ts`: `CommandBus`, `QueryBus`, `SessionsRepository` и `PasswordService` замоканы:

- при регистрации на занятый email возвращается 409;
- логин с неверным паролем и с несуществующим email даёт одинаковую 401;
- повторное использование refresh-токена отзывает все сессии;
- смена пароля с неверным текущим паролем даёт 401, а при успехе отзываются остальные сессии.

Плюс `jwt-auth.guard.spec.ts`: публичный маршрут пропускается, без cookie возвращается 401, с отозванной сессией возвращается 401.

## Проверка

1. `npm install` и `npm run prisma:migrate -w @balance/api -- --name auth`.
2. `npm run typecheck && npm run lint && npm run test -w @balance/api`.
3. `npm run dev -w @balance/api`, затем сценарий через curl с cookie jar (`-c/-b jar.txt`):
   - register, затем `GET /auth/me` возвращает 200;
   - logout, затем `/auth/me` возвращает 401;
   - login, затем refresh; повторный refresh старым токеном даёт 401, и после этого `/auth/me` тоже 401;
   - смена пароля, затем логин со старым паролем даёт 401, с новым 200.
